# 07 — Vision

Product direction for FlowFlow. Intelligence-first, not cosmetic-first.

## One-Line Pitch

**FlowFlow: capture by voice, import documents, chat with your knowledge. Local-first RAG on iPhone.**

## Core MVP

1. **Voice notes** with transcription (done)
2. **Text editing** with folders (done)
3. **Document import** — feed PDFs, text files, docs into the knowledge base
4. **Tags** — interconnected with folders and RAG, auto-generated by LLM
5. **RAG Chat** — ask questions, get answers from your notes and documents

Everything else is post-MVP.

## Three Differentiators

### 1. Global Notes (No Voice/Text/Document Dichotomy)
A note is a note. A document is a document. But they all feed the same intelligence layer.
- Voice input, keyboard input, file import — all become searchable knowledge
- Tags connect everything: notes, documents, folders
- The RAG doesn't care about the source — it searches across all content

### 2. Scoped Intelligence
Most RAG apps have one flat search. FlowFlow has context-aware intelligence:
- **Global chat**: search everything
- **Folder chat**: "I'm in the Work folder, answer from Work content only"
- **Tag chat**: "Search only #meeting content"
- **Combined**: folder + tag filtering
- No need to manually reference scope when already inside a folder

### 3. French-First
- Soniox stt-async-v4 with `language_hints_strict: true`
- AI titles, tags, and cleanup in natural French
- Date formatting: "8 mai 2026, 14:30"
- LLM responses in French

## RAG Architecture

### Data Flow
```
Voice note → Soniox → transcript → AI (title + tags + cleanup) → SQLite + Embed → LanceDB
Text note  → save                 → AI (title + tags)          → SQLite + Embed → LanceDB
Document   → import → extract text → AI (title + tags)         → SQLite + Embed → LanceDB
```

All three paths converge into the same vector store. Chat queries search across all of them.

### Tag Interconnection Model
```
Tags ←→ Notes      (auto-generated + manual)
Tags ←→ Documents  (auto-generated + manual)
Tags ←→ Folders    (default tags per folder)
Tags → RAG filter  (scope vector search by tag)
```

Tags are the connective tissue. They're not cosmetic labels — they're RAG metadata.

### Chat Scoping
```
User is on main screen → Chat = global
User is in "Work" folder → Chat = folder-scoped (automatic)
User types @#meeting → Chat = tag-scoped
User types @Work → Chat = folder-scoped (explicit)
User in "Work" + types @#budget → Chat = folder + tag combined
```

The simplest UX: if you're in a folder, chat already knows the context.

## Future Considerations

### REST API / Web Interface
The `services/` layer (ai.rs, vectordb.rs, chat.rs) has no Dioxus dependency.
It can be exposed as a REST API via `axum` or `actix-web`:

```
POST /api/chat      → { question, scope } → { answer, sources }
GET  /api/notes     → list notes with tags
GET  /api/search    → hybrid FTS5 + semantic search
POST /api/import    → upload document
```

This enables:
- Web interface to chat with notes from desktop
- API for integrations (Shortcuts, Zapier, n8n)
- Sync/migration between devices
- Multi-device access to the same knowledge base

### Architecture for Portability
```
models/     → pure Rust domain entities
db/         → SQLite persistence (no UI dependency)
services/   → AI, vectors, chat, audio, transcription (no UI dependency)
platform/   → iOS-specific (objc2)
ui/         → Dioxus components (only layer tied to framework)
```

If SwiftUI port needed: rewrite `ui/` only, keep everything else as Rust `staticlib`.
If web API needed: add `api/` layer that calls `services/` directly.

## What NOT to Build (MVP Scope)

- Photo/camera attachments (post-MVP)
- Markdown rendering (not needed)
- JS libraries (not needed)
- Drag-and-drop (not mobile-appropriate)
- Pin/toast/timeline cosmetics (not MVP)
- Dark mode (after intelligence works)
- Export (after intelligence works)
- Apple Watch / Siri / widgets (different product)
- CRDT sync (premature)
- Graph view (needs backlinks + embeddings first, post-MVP)
